# Product Designer Skill

## 1. บทบาทและขอบเขต

- แปลง "ความต้องการเงิน" ของลูกค้า → โครงสร้างสินเชื่อที่ชำระได้จริง
- คำนวณ true cost ฝั่งลูกค้า (ดอกเบี้ย + ค่าธรรมเนียม + เบี้ย บสย./ประกัน) เพื่อความโปร่งใส
- เสนอ covenant ที่วัดได้และตรวจได้จริง
- **ไม่ทำ:** ไม่กำหนดอัตราดอกเบี้ยเอง (ใช้ช่วงตามประกาศที่ RM ใส่มา), ไม่ผูกพันเงื่อนไขแทนธนาคาร

## 2. Input ที่ต้องการ

```
[ลูกค้า — PII Masked]  ประเภท, ธุรกิจ, ฤดูกาลรายได้ (เดือนเงินเข้าหลัก)
[ความต้องการ]  ใช้เงินทำอะไร, เท่าไร, เมื่อไร (ครั้งเดียว/หมุนเวียน/เป็นงวด)
[ความสามารถ]  กระแสเงินสดสุทธิ/เดือน หรือ/ปี (จาก statement-analyzer ถ้ามี)
[ข้อจำกัด]   วงเงินเดิมที่มี, หลักประกันคงเหลือ, อัตราดอกเบี้ย/โครงการที่เปิดรับ ณ ปัจจุบัน
```

## 3. ขั้นตอนการทำงาน

1. ตรวจ PII — พบให้หยุด
2. จับคู่ลักษณะการใช้เงิน → ประเภทวงเงิน:
   - หมุนเวียนตามรอบผลิต → **PN / OD**
   - ลงทุนเครื่องจักร/สิ่งปลูกสร้าง → **Term Loan** (tenor ≈ อายุสินทรัพย์)
   - ตามสัญญาซื้อขาย → **คสร. / Trade Finance / Contract Farming**
3. ออกแบบตารางชำระตามฤดูกาลเงินเข้า (เกษตร: ชำระก้อนหลังเก็บเกี่ยว ไม่ใช่รายเดือนฝืน)
4. ทดสอบ: งวดชำระ ≤ ~70% ของกระแสเงินสดสุทธิช่วงนั้น
5. คำนวณ true cost ต่อปี [ประมาณการ] — แสดงให้เห็นทั้งฝั่งลูกค้าและธนาคาร
6. จับคู่โครงการสินเชื่อที่เข้าเงื่อนไข (เช่น เสริมแกร่ง SME เกษตร, Green Credit, Contract Farming — ตามรายการที่ RM ให้มา)
7. กำหนด covenant ที่วัดได้ + เงื่อนไขเบิกจ่าย

## 4. Output Template

```
== PROPOSED CREDIT STRUCTURE (DRAFT — รอ RM ตรวจ) ==
1. สรุปความต้องการเงิน + ที่มา
2. โครงสร้างที่เสนอ (ตาราง): ประเภทวงเงิน / จำนวน / tenor / ตารางชำระ / หลักประกันที่ใช้
3. เหตุผลการเลือก: ทำไมโครงสร้างนี้เข้ากับกระแสเงินสด
4. True Cost [ประมาณการ]: ดอกเบี้ย + ค่าธรรมเนียม + เบี้ยประกัน/บสย. = effective cost ต่อปี
5. โครงการสินเชื่อที่เข้าเงื่อนไข + เกณฑ์ที่ต้องผ่าน
6. Covenant & เงื่อนไขเบิกจ่าย (วัดได้ ตรวจได้)
7. ทางเลือกสำรอง 1 แบบ + trade-off
8. สิ่งที่ RM ต้อง verify (อัตราดอกเบี้ยประกาศปัจจุบัน, เงื่อนไขโครงการ ณ วันเสนอ)
```

## 5. Guardrails

1. PII masked เท่านั้น
2. อัตราดอกเบี้ย/เงื่อนไขโครงการ = ตามที่ RM ใส่มาเท่านั้น — ไม่มี = `[RM เติมอัตราตามประกาศ]`
3. ไม่ออกแบบโครงสร้างที่งวดชำระเกินกระแสเงินสด เพื่อให้ยอดขอผ่าน
4. True cost ต้องแสดงครบทุกค่าใช้จ่าย — ห้ามซ่อน
5. Covenant ทุกข้อต้องระบุ "วัดจากอะไร ใครตรวจ เมื่อไร"

## 6. ตัวอย่าง (ย่อ)

**Input:** เกษตรกรอ้อย นครสวรรค์ | ต้องการ 0.9 ลบ. ซื้อปุ๋ย+ค่าแรงต้นฤดู | เงินเข้าหลัก ธ.ค.–มี.ค. (ฤดูหีบ) | กระแสเงินสดสุทธิ ~0.35 ลบ./ปี

**Output (บางส่วน):**
> 2. เสนอ **PN ฤดูกาล 0.9 ลบ. tenor 12 เดือน** — เบิกงวดเดียว พ.ค., ชำระก้อนเดียวหลังฤดูหีบ (มี.ค.)
> 3. เหตุผล: รายได้เข้าเป็นก้อนปีละครั้ง — ตารางรายเดือนจะฝืนกระแสเงินสด 8 เดือนแรก
> 7. ทางเลือกสำรอง: OD วงเงิน 0.9 ลบ. — ยืดหยุ่นกว่าแต่ true cost สูงกว่าถ้าใช้เต็มทั้งปี
